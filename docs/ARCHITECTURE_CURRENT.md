# Архитектура baseline: как устроен бот сейчас

Проект `26-08-vdm-bot`, коммит `6502846` от 02.09.2026. Документ описывает код
на 12.09.2026, а не исходный замысел. Составлен по чтению всех файлов `src/`,
`tests/`, `run.py`, конфигурации и собранных данных. Данные открывались только
на чтение, код не менялся.

Связанные документы: [BASELINE.md](BASELINE.md) — зафиксированное состояние,
[AUDIT.md](AUDIT.md) — оценка по компонентам, [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) — план v2.

## 1. Общая схема

```text
 Telegram (aiogram 3, long polling)      Виджет на сайте                 MAX
 src/adapters/telegram/bot.py            src/web/static/widget.js        src/adapters/max/
                                         → src/web/app.py (FastAPI)      (пустой пакет)
                                           src/web/render.py
            │  handle_text / handle_action          │
            └───────────────────┬───────────────────┘
                                ▼
              src/core/dialog.py — DialogEngine (синхронный)
   команды · постоянная клавиатура · профиль задачи · корзина · оформление
   · согласие на ПДн · /my_data · /delete_data · выдача по 3 позиции
        │                 │                   │                    │
        ▼                 ▼                   ▼                    ▼
  src/agent/         src/catalog/        src/norms/           src/orders/
  SalesAgent         CatalogIndex        documents            OrderService
  Router (роль)      (в памяти процесса) reference (справка)  sinks: Jsonl + Xlsx
  ToolBox, verify    search, text        items (пункты)       (+ Google Sheets,
  providers          models              extract (привязка)    Bitrix24 — заглушка)
        │                 ▲                   ▲
        ▼                 │                   │
  Cloud.ru → OpenRouter   src/ingest/ build_kb: выгрузка 1С (xlsx) → data/kb/products.jsonl
  (OpenAI-совместимый)    norm_registry: реестр «пункт 1057 → код 1С» (PDF)
                          norms/items: тексты приказов 838 и 1057 (PDF) → norm_items.json

  src/core/storage.py  — SQLite: carts, orders, consents, dialog_state,
                          product_media, product_attributes, telegram_photos
  src/media/           — фото и характеристики со страниц vdm.ru → SQLite-кэш
                          → файлы data/media/<код>/N.jpg → копия в products.jsonl
  src/privacy/         — маскирование ПДн (Masker), текст согласия с версией
  src/observability/   — журнал диалогов JSONL по суткам
```

Всё собирается в одной точке: `src/core/app.py:build_engine`. Адаптеры получают
готовый `DialogEngine` и не знают, как он устроен.

## 2. Ход диалога: текстовое сообщение

`DialogEngine.handle_text(user_id, channel, text)`:

1. Сбрасываются счётчики хода `session.usage` и `session.route`.
2. `/команда` → `_handle_command` (`/start`, `/menu`, `/cart`, `/order`,
   `/manager`, `/my_data`, `/delete_data`, `/help`).
3. Идёт сбор контактов (`checkout_step`) → `_collect_contact`, шесть полей.
4. Нажатие постоянной клавиатуры Telegram приходит текстом → `KEYBOARD_ACTIONS`.
5. `profile.update_from_text(text)` — регулярками достаются учреждение, зона,
   возраст, документ, бюджет, срок, регион, отказ.
6. `session.remember("user", text)` — реплика пишется в историю **уже
   маскированной**.
7. Ветвление:
   - вопрос о документе (`norms.reference.question_about_document`) → справка
     `_explain_norm` без обращения к модели;
   - агент есть → `SalesAgent.reply`;
   - агента нет → `offer()`: классификация `core/intent.py` и честный ответ без
     модели. На приветствие товаров нет, на предметный запрос — до 10
     наименований и три карточки.
8. `_remember(session)` — история и профиль сохраняются в SQLite.
9. Ход пишется в журнал `DialogLogger.turn`.

`SalesAgent.reply` (`src/agent/agent.py`):

1. Все провайдеры в паузе → `engine.offer()`.
2. `Router.decide` (`src/agent/routing.py`): сначала правила, модель вызывается
   только на неоднозначном. Решение записывается в профиль: stage, objection,
   ready_to_see.
3. `may_show_cards` — гейт карточек: роль продавца, возражение снято, клиент
   готов смотреть, известны учреждение и зона (или назван точный пункт).
4. Системный промпт роли (`ROLE_PARTS`) + `profile.as_prompt()` + последние 12
   реплик.
5. `_ask` — провайдеры по очереди; `_run` — цикл вызова инструментов, до 4 кругов.
6. `_verified` — каждая сумма и каждая ссылка «пункт N приказа M» в ответе
   сверяются с тем, что вернули инструменты за весь разговор. Одна попытка
   переписать; вторая неудача → выдача каталога.
7. `masker.unmask` → `_render`: карточки только тех товаров, которые модель
   назвала (по коду или паре слов названия), не больше трёх. Если продавец
   перечислил товар общими словами без поиска, дописывается настоящая выдача.

### Правила маршрутизатора

| Реплика | Роль | Чем решено |
|---|---|---|
| пусто | консультант | правило |
| попытка инъекции (`_INJECTION`) | защита, без инструментов | правило |
| приветствие, вежливость | консультант | `intent.classify` |
| вопрос о документе / пункте | консультант | `intent.classify` |
| номер пункта перечня | продавец, `precise=True`, показ разрешён | `intent.classify` |
| прямая просьба показать / слова товара | продавец, показ разрешён | `intent.classify` |
| остальное (возражения, согласия, ответы) | по JSON от модели, `max_tokens=200` | модель; сбой → продавец |

### Роли и инструменты

| Роль | Части промпта | Инструменты |
|---|---|---|
| `consult` | guard + common + consultant | `explain_norm`, `find_norm_item`, `get_cart`, `handoff_to_manager` |
| `sell` | guard + common + salesman | все восемь |
| `guard` | guard | нет |

Инструменты (`src/agent/tools.py`): `search_products`, `find_by_norm_code`,
`find_norm_item`, `explain_norm`, `get_product`, `add_to_cart`, `get_cart`,
`handoff_to_manager`. Оформление заказа агент не выполняет: его подтверждает
пользователь кнопкой.

## 3. Нажатия кнопок

`DialogEngine.handle_action(user_id, channel, "глагол:аргумент")`:

| Действие | Что делает |
|---|---|
| `menu`, `catalog`, `root:N` | меню, корневые разделы, раздел по номеру |
| `norms`, `norm_doc:ID`, `norm_items:ID` | выбор документа, справка, позиции по документу |
| `card:SKU` | подробная карточка со всеми основаниями |
| `add:SKU`, `inc:`, `dec:`, `del:` | корзина (сообщение правится на месте) |
| `card_inc:`, `card_dec:` | количество прямо в карточке |
| `cart`, `clear` | показать / очистить корзину |
| `restart` → `restart_yes` | начать заново с подтверждением |
| `manager` | контакты менеджера |
| `checkout` → `consent_yes`/`consent_no` → поля → `confirm_order`/`cancel` | оформление |
| `more:N` | следующие три позиции той же выдачи |
| `noop` | надпись с количеством, ответа нет |

Примитивы ответа (`src/core/ui.py`): `Message`, `ProductCard`, `ProductList`,
`OrderSummary`, `Keyboard`/`Button`. Лимит раскладки взят по MAX: до 7 кнопок в
ряду, до 3 кнопок-ссылок. Telegram рисует карточки с фото, виджет — строки
заявки, данные у обоих одинаковые.

## 4. Данные и источники истины (как есть)

| Данные | Откуда | Где хранится | Кто пишет | Замечание |
|---|---|---|---|---|
| Код 1С, наименование, цена, остаток, URL, описание, дерево каталога | выгрузка 1С `Pricelist*.xlsx`, лист 1, колонки A–G | `data/kb/products.jsonl` | `run.py ingest` | файл **перезаписывается целиком**; цена округляется до целых рублей; пустой остаток превращается в 0; колонки «Артикул» нет |
| ID элемента Битрикса | лист 2 той же выгрузки | `products.jsonl`, поле `bitrix_id` | `ingest` | берётся по совпадению наименования, неоднозначные отбрасываются |
| Фото, характеристики (страна, сертификат) | страницы vdm.ru: `og:image`, галерея, `propertyList` | SQLite `product_media`, `product_attributes`; файлы `data/media/<код>/N.jpg`; копия в `products.jsonl` | `run.py media`, лениво при показе карточки | при пересборке переносятся из прежнего `products.jsonl` |
| Нормативная привязка товара | заголовки прайса, номер в URL, текст описания, корень каталога, реестр «Иван» (PDF) | `products.jsonl`, поле `norms` (+ `data/kb/norms_1057.json`) | `ingest`, `run.py norms` | у каждой ссылки `source` и `confidence` (`SOURCE_WEIGHTS`) |
| Формулировки пунктов приказов | PDF приказов 838 и 1057 | `data/kb/norm_items.json` | `run.py acts` | для 1057 разобраны единица и количество |
| Справка по документам | написана в коде | `src/norms/reference.py`, `documents.py` | разработчик | ждёт подписи методиста (`НОРМАТИВКА_НА_ПОДТВЕРЖДЕНИЕ.md`) |
| История и профиль разговора | — | SQLite `dialog_state` + память процесса | ядро | история маскирована, срок 30 дней, чистка при старте |
| Корзина | — | SQLite `carts`, ключ `user_id` **без канала** | ядро | цена фиксируется при добавлении |
| Заказ | — | SQLite `orders` + `data/orders.jsonl` + `data/orders/<номер>.xlsx` (+ Google Sheets) | `OrderService` | статусы `new` / `sent` / `failed` |
| Согласия | — | SQLite `consents`, только добавление | ядро | версия текста `2026-08-27.v1` |
| Журнал диалогов | — | `data/dialogs/ГГГГ-ММ-ДД.jsonl` | `DialogLogger` | id пользователя → sha256-псевдоним, ПДн маскируются |

**Выгрузка 1С сейчас является единственным источником цены и остатка.** Модель
цены не выдумывает: суммы в ответе сверяются с результатами инструментов.

## 5. Нормативная модель

- Реестр документов `src/norms/documents.py`: `order_838` (школы),
  `order_1057` (детские сады), `fgos_do`, `fop_do`, `func_kits` (сады).
- `documents.for_audience(audience)`: сад — 1057, ФГОС ДО, ФОП ДО, функциональные
  комплекты; школа — только 838; аудитория неизвестна — все.
- Аудитория разговора (`DialogProfile.audience`) определяется так, по убыванию
  надёжности: документ, по которому человек закупает → тип учреждения → кабинет.
  Документ, о котором человек только **спросил**, аудиторию не меняет
  (`asked_about_docs`).
- Индекс каталога хранит пункты по ключу «(документ, пункт)», а не по голому
  номеру (`CatalogIndex._by_norm_code`). Названный документ отсекает жёстко,
  аудитория — по списку документов.
- Инструменты отвечают «пункта нет в этом приказе, есть в другом», а не
  подставляют похожий.
- Ссылка на пункт в ответе модели проверяется так же, как цена
  (`agent/verify.py:invented_norm_refs`).
- Реестра «пункт 838 → код 1С» у заказчика нет. Привязка к 838 берётся из
  дерева каталога сайта.

## 6. HTTP и каналы

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | число товаров, включена ли модель, приёмник заказов |
| POST | `/widget/session` | анонимный `session_id` (hex32), приветствие, текущая корзина |
| POST | `/widget/message` | текст → ответы ядра |
| POST | `/widget/action` | кнопка → ответы ядра |
| GET | `/media/{sku_1c}` | снимок товара с диска |
| GET | `/widget.js` | скрипт виджета, `Cache-Control: no-cache` |
| GET | `/demo` | демо-страница |

Swagger отключён (`docs_url=None`). Меню команд Telegram: `/start`, `/help`,
`/cart`, `/order`, `/manager`; постоянная клавиатура: «Каталог», «Моя корзина»,
«Менеджер». Telegram вызывает синхронное ядро через `asyncio.to_thread`,
индикатор «печатает» повторяется, при обрыве связи запросы повторяются.

## 7. Деградация

- Нет ключа модели → агент не создаётся, ядро отвечает через `offer()`.
- Сбой провайдера → пауза 300 с (402 «нет денег» — тоже 300 с), отказ ключа
  401/403 — 1800 с; ход уходит следующему провайдеру.
- Все провайдеры в паузе → `offer()`.
- При запуске Telegram и виджета провайдеры прогреваются коротким вызовом.
- Справка по документам работает без модели всегда.

## 9. Ограничения конструкции, важные для v2

1. **Каталог в процессе неизменяем.** `load_index` закэширован через
   `lru_cache`, новая выгрузка видна только после перезапуска виджета и
   Telegram-бота.
2. **Версий каталога нет.** Нет истории цен и diff. `ingest` перезаписывает
   `products.jsonl`, товары, пропавшие из выгрузки, исчезают бесследно, хотя
   `ПЛАН.md` обещает помечать их архивными.
3. **Корзина хранит цену на момент добавления** и не пересчитывается.
4. **Заказ не знает, по какой версии каталога собран.**
5. **Количества как понятия нет.** В корзину добавляется 1 шт., дальше кнопки
   «±». Количества из приказа 1057 разобраны, но нигде не используются.
6. **Пользователей, ролей и аутентификации нет.** Идентификатор в виджете —
   строка от клиента.
7. **Ядро синхронное.** На процесс одно SQLite-соединение
   (`check_same_thread=False`) без блокировки, а вызывают его из нескольких
   потоков.
8. **Состояние наличия двузначное:** «в наличии N шт.» или «под заказ».
   «Неизвестно» от «нет» не отличается.
9. **Загрузки файлов от пользователя нет** ни в одном канале.
