# Решения по вопросам аудита

Приняты заказчиком разработки 12.09.2026 по итогам [AUDIT.md](AUDIT.md). Имеют
приоритет над вариантами в [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md), где
они расходятся.

---

## D1. Tilda — не используется

- vdm.ru работает на 1С-Битрикс. В коде, архитектуре и материалах Tilda не
  обнаружена.
- `TildaAdapter` не реализуется. Предположения о Tilda API и Tilda CRM не
  делаются. Tilda не является источником истины и не блокирует v2.
- Создаются только интерфейсы `CatalogSource`, `CardSource`, `CRMAdapter`,
  `NotificationChannel`.
- Реализации текущего этапа: `OneCSource` (цены, наличие, коды),
  `BitrixSiteCardSource` (карточки, описания, фото), адаптеры поверх
  существующих приёмников заказов.
- Статус Tilda: **UNKNOWN / NOT IMPLEMENTED**. Если заказчик предоставит данные
  (что на Tilda, URL, API, доступы, формат, сценарий CRM), это оформляется
  отдельной задачей интеграции.

## D2. Промпты v2 — ещё не переданы

- Найденные материалы — промпт бота «Иван», промпт-оценщик сделок, расшифровка
  вебинара — используются только как справочные. Финальными промптами v2 они
  не считаются.
- Разработка их не ждёт. Слой промптов изолирован: тексты лежат в
  `src/agent/prompts/{common,consultant,salesman,router,guard}.md` и читаются
  загрузчиком. В Python содержание промптов не зашивается.
- Финальные промпты v2 заменят файлы без изменения бизнес-логики.

## D3. Репозиторий — новый, приватный

- Создаётся новый репозиторий GitHub `12-09-vdm-bot`, **PRIVATE**. Публичный

- Схема: `26-08-vdm-bot` → локальный клон → очистка и аудит → `12-09-vdm-bot`
  → новый приватный репозиторий.
- Перед публикацией обязательно: `git status`, `git diff`, `git log`,
  `gitleaks` по всей истории — с учётом отозванного токена Telegram в истории
  исходника. Секреты не переносятся.
- Статус на 12.09.2026:

  - история перенесена **чистой**: первый коммит `2fbbefc` содержит дерево

## D4. База данных — SQLite до EPIC 4 за репозиториями

- EPIC 0–4 работают на SQLite. PostgreSQL рассматривается перед EPIC 5 или
  перед многопользовательским продом.
- Обязательное условие: `Application Service → Repository Interface → SQLite
  Repository`. Прямые `sqlite3.connect` / `cursor.execute` в бизнес-модулях
  запрещены. Переход на PostgreSQL — это замена реализации репозитория, логика
  при этом не меняется.

## D5. Бот читает только утверждённый каталог

- Конвейер: RAW IMPORT → VALIDATION → NORMALIZATION → MATCHING → DIFF →
  ADMIN REVIEW → APPROVAL → APPROVED SNAPSHOT → CatalogIndex → BOT.
- Сырой импорт не меняет данные бота. Утверждение создаёт
  `data/kb/versions/<версия>/products.jsonl`, а `data/kb/current` переключается
  атомарно. После утверждения `CatalogIndex` обновляется без перезапуска
  процессов, минимально инвазивно.

## D6. EPIC 0.5 — только R1 и регрессионные тесты

- Исправить R1 минимально, виджет не переписывать. Добавить регрессионные
  тесты, прогнать весь набор и ruff, закоммитить, **остановиться**.
- EPIC 1 не начинать без отдельной команды.

## D7. Уточнения к модели v2 (из того же ответа)

- **`/start`** сбрасывает текущую задачу, этап и подбор. Историю, прежние
  заказы, документы и аудит не трогает. Сейчас `/start` очищает и корзину —
  это меняется только после отдельного теста и без удаления исторических данных.
- **Task profile** расширяет существующий `DialogProfile`. Вторая параллельная
  система состояния не создаётся, поля без необходимости не добавляются.
- **Порядок работы в каждом EPIC:** ANALYZE → IMPLEMENT → TEST → REGRESSION →
  RUFF → DOCUMENT → COMMIT → STOP. Одним проходом всё сразу не делается.
- **Заказ клиента на входе:** сначала Excel и CSV. Word и PDF — по реальным
  образцам заказчика.
- **Таблицы БД** создаются только те, что нужны конкретному EPIC.

## D8. Catalog Domain (EPIC 1)

Принято 12.09.2026 по итогам анализа EPIC 1 (решения A–E).

### Контракт товара

Второй модели нет: расширен `catalog.models.Product`. Новые поля — `sources`,
`stock_known`, `is_active` — стоят в конце и имеют значения по умолчанию,
остальное — свойства поверх уже собранных данных. Формат `products.jsonl`
прежний, старые записи читаются.

| Поле контракта | В `Product` | Откуда сейчас |
|---|---|---|
| `id`, `article` | `sku_1c` — код 1С | выгрузка каталога |
| `name`, `price`, `currency` | как было | выгрузка каталога |
| `availability`, `quantity_available` | из `in_stock` и `stock_known` | выгрузка каталога |
| `description`, `kit_contents`, `url` | как было | выгрузка каталога, колонки карточки |
| `image_urls`, `characteristics` | `images`, `attributes` | страница товара |
| `supplier_article`, `manufacturer` | атрибуты «Артикул», «Бренд» | страница товара |
| `institution_types`, `rooms`, `age_ranges` | `catalog/placement.py` и атрибут «Возраст» | дерево разделов, страница товара |
| `norm_documents`, `norm_points` | из `norms` | нормативная привязка |
| `source`, `source_id` | `commercial.source`, `card.sources`, `placement_source` | — |
| `is_active` | поле, по умолчанию `true` | — |

Не добавлены:
- `zones` — разметки зон в данных нет;
- `category` / `subcategory` одним значением — у 1 166 товаров несколько
  размещений; вместо них `placements` и фильтр `category` по любому разделу;
- `metadata` — уже есть `updated_at` и `sources`.

### Источники истины

| Группа полей | Владелец по ТЗ | Сейчас поставляет | `SourceRef.kind` |
|---|---|---|---|
| Артикул, название, цена, наличие | 1С (`OneCSource` — позже) | выгрузка `Pricelist*.xlsx` | `catalog_export` |
| Описание, состав комплекта, URL | карточка сайта (`BitrixSiteCardSource` — позже) | та же выгрузка | `catalog_export` |
| Фото, характеристики, артикул поставщика, бренд, возраст | карточка сайта | страница товара | `site_page` |
| Учреждение, кабинет, возраст группы | дерево каталога заказчика | выгрузка | `catalog_tree` |
| Нормативные основания | нормативный домен | `NormRef` со своим `source` | — |

- Коммерческие данные (`CommercialData`) нормативных полей не содержат.
- Карточка (`CardData`) — отдельный объект и расширяется независимо от 1С.
- С интеграцией 1С меняется поставщик данных, а не контракт.

### Решения

- **A. `article = sku_1c`.** Подтверждено данными: атрибут карточки «Код»
  совпадает с кодом 1С. «Артикул» сайта — артикул поставщика
  (`supplier_article`). Он неуникален, ключом не служит, по нему не ищем.
- **B. Пока интеграции с 1С нет, источник — карточки.** Описание и состав
  комплекта считаются данными карточки, пришедшими выгрузкой каталога.
- **C. Размещение — по дереву разделов заказчика**, не по нормативному
  движку:
  - учреждение и кабинет проверяются на одном и том же размещении;
  - кабинет берётся с самого глубокого раздела, где он назван: в «Оснащении
    новостроек» кабинеты вложены в «1.6 Бассейн»;
  - незнакомое название раздела — «не определено», без догадок;
  - предметный кабинет узнаётся только со словом «кабинет», поэтому
    сюжетная игра «02.16 Мастерская» кабинетом труда не считается.
- **D. Каждый заданный фильтр попадает в отчёт** `CatalogResult.filters`:
  - статусы: `applied`; `partial` — у части кандидатов нет данных, и сказано,
    оставлены они или исключены; `not_applied`;
  - жёсткие фильтры: учреждение, кабинет, раздел, норматив, производитель,
    цена, наличие — товар без данных исключается;
  - мягкий фильтр — возраст: исключается только товар, чей известный возраст
    противоречит запросу;
  - не применяются: зона (разметки нет) и название учреждения;
  - нераспознанное значение (учреждение «колледж», помещение «столовая»,
    «приказ 999») даёт пустую выдачу с пояснением, а не весь каталог;
  - цена и наличие, названные в тексте запроса («до 2000 руб», «в наличии»),
    становятся полями запроса и тоже попадают в отчёт.
- **E. `UNKNOWN` для наличия — сразу, не в EPIC 2:**
  - `ingest` пишет пустую ячейку остатка как `null` (раньше писал 0), отчёт
    загрузки считает `stock_unknown`;
  - прежние потребители видят 0 и пишут «под заказ»;
  - `UNKNOWN` не проходит фильтр «в наличии»;
  - в выгрузке от 26.08.2026 пустых ячеек нет (5 269 нулей и 3 217
    положительных), поэтому на текущих данных поведение бота не меняется.

### Слои

- `CatalogService` делит подбор на стадии: `retrieve` → `filter` → `rank` →
  `present`.
- Сервис работает через `CatalogRepository` (Protocol). Реализация —
  `InMemoryCatalogRepository` поверх прежнего `CatalogIndex`.
- SQLite каталог не использует; смена хранилища — новая реализация
  репозитория.
- `DialogEngine.catalog` отдаёт сервис; бот и агент на него пока не переведены.

### Замер на реальном каталоге (5 936 товаров)

- «Оборудование для кабинета информатики», школа:
  - прежний поиск — 1 товар раздела в топ-10;
  - сервис с кабинетом — все 12 товаров раздела, ни одного чужого.
- «Кабинет химии», школа — все 17 товаров раздела.
- Кабинет определён у 2 312 товаров, возраст — у 1 846.

### Ограничения

- **Фильтр верит раскладке заказчика.**
  - Садовские мячи из «12.04 Мячи» кабинетом не размечены, поэтому в
    «спортивный зал для сада» не попадают. Отчёт фильтра это показывает:
    86 исключены «нет данных».
  - В «Кабинете химии» лежат садовские пипетки.
- **Бренд заполнен у 40 товаров**, поэтому фильтр по производителю почти
  всегда `partial`.
- **Нормативные ссылки** физически по-прежнему в записи товара; разнести их —
  EPIC 4 и 7.
- **R5 остаётся:** новые тесты данных не читают, но `test_web.py` по-прежнему
  читает `data/kb`.
