# Персональные данные: где обрабатываются и чем это подтверждается

Записка для службы безопасности заказчика. Это **не юридическое заключение**:
здесь описано, как система устроена технически и где в коде это видно. Выводы о
соответствии 152-ФЗ делает юрист заказчика по своей модели обработки.

Дата: 19.09.2026. Состояние: виджет работает на сервере в РФ, Telegram-канал
поднят, выход к api.telegram.org с сервера восстанавливается (см. «Транзит»).

## 1. Контур

```
Посетитель сайта                  Пользователь Telegram
      │                                  │
   браузер                          Telegram (Bot API)
      │ https                            │ https
      ▼                                  ▼
┌─────────────────────────────────────────────────┐
│  Сервер в РФ (Selectel, ru-7a, 135.106.222.191) │
│  nginx → виджет (uvicorn) · Telegram-модуль     │
│  ядро диалога · SQLite: корзины, заказы,        │
│  согласия, история разговоров                   │
└───────────────────────┬─────────────────────────┘
                        │ https, только обезличенный текст
                        ▼
              Cloud.ru Foundation Models (РФ)
```

Всё, что система записывает и хранит, лежит на сервере в РФ. Иностранных узлов
**нашей** обработки нет: ни шлюзов, ни очередей, ни резервных копий за рубежом.

## 2. Что происходит с данными — и где это в коде

| Свойство | Как сделано | Файл |
|---|---|---|
| Первичная запись и хранение — в РФ | SQLite на сервере Selectel, резервная копия снимается туда же | `src/core/storage.py`, `deploy/README.md` |
| Обезличивание до отправки в модель | телефон, e-mail, ИНН, ФИО заменяются метками; маска ставится **при записи** истории, а не перед вызовом модели | `src/privacy/masking.py`, `src/core/dialog.py` (`Session.remember`) |
| Возврат значений пользователю | метки раскрываются в ответе; нераскрытая метка заменяется нейтральным словом, а не значением | `Masker.unmask`, `src/agent/agent.py` |
| Согласие с версией текста | в журнале хранится не «согласился», а редакция текста, на которую согласился | `src/privacy/consent.py` (`CONSENT_VERSION`), `storage.record_consent` |
| Права субъекта | `/my_data` — выгрузка, `/delete_data` — удаление и отзыв согласия; заказы обезличиваются, строки спецификации остаются | `src/core/dialog.py`, `src/core/storage.py` |
| Журнал диалогов | пишется маскированным, отключается настройкой `DIALOG_LOG_MASK_PDN` | `src/observability/dialog_log.py` |
| Секреты вне журналов | токен бота, ключи моделей, пароль почты и адрес транзита маскируются на входе в журнал | `src/observability/redact.py`, `Settings.secret_values` |
| Шаги сбора контактов не логируются | вместо текста в журнал идёт отметка о шаге | `src/core/dialog.py` (`handle_text`) |

Пример обезличивания, который можно показать на демонстрации:

```
в переписке:  «Иван Петров, +7 900 111-22-33, пришлите счёт на ivan@example.ru»
в модель:     «[ИМЯ_1], [ТЕЛЕФОН_1], пришлите счёт на [EMAIL_1]»
```

## 3. Кто получает данные

| Получатель | Что получает | Где | Основание/условие |
|---|---|---|---|
| Сервер заказчика (Selectel) | всё: переписка, контакты, заказы | РФ | своя инфраструктура |
| Cloud.ru Foundation Models | обезличенный текст хода | РФ | договор с Cloud.ru |
| Почта менеджеров (`ORDER_SINK=smtp`) | заявка с контактами и спецификацией | почтовый сервис заказчика | заявка адресована самому заказчику |
| Telegram | всё, что пользователь пишет боту в Telegram | инфраструктура Telegram | выбор канала заказчиком |
| OpenRouter | **по умолчанию выключен**: на сервере `LLM_PROVIDER=cloudru` | зарубеж | включать только для обезличенных запросов и по отдельному решению |

О Telegram стоит сказать прямо: как только заказчик выбрал Telegram каналом
общения, данные пользователя проходят через инфраструктуру Telegram — независимо
от того, где стоит наш сервер. Наша часть архитектуры на это не влияет; влияет
она на то, где данные **записываются и хранятся**, а это РФ.

## 4. Транзит до Telegram

С сервера Selectel api.telegram.org не открывается (тихий таймаут; Cloud.ru с того
же сервера отвечает за 2,3 с). Решение — не выносить Telegram-модуль за границу, а
пропустить исходящие запросы через транзит: `TELEGRAM_PROXY`, SOCKS5 или HTTP
CONNECT (`src/adapters/telegram/bot.py::_session`).

Почему транзит — не обработчик персональных данных:

- соединение TLS сквозное, от нашего сервера до Telegram; транзит пересылает
  зашифрованные байты и расшифровать их не может;
- ни переписки, ни контактов, ни токена бота он не видит и не хранит;
- на самом узле нет ни базы, ни очереди, ни журналов с телом запросов.

Требования к узлу: вход разрешён только с адреса сервера (ufw), исходящие — только
на 443, авторизация по логину и паролю, журналы без тела запросов. Предпочтительно
российский адрес; зарубежный тоже не создаёт иностранного узла обработки, но
российский снимает вопрос ещё и формально.

Что **не** делаем: не выносим Telegram-модуль на иностранный сервер. Такой сервер
принимал бы `update` целиком — текст, имя, username, телефон, файлы — и был бы
самостоятельным обработчиком ПДн за рубежом, даже если «ничего не хранит»: данные
всё равно оказываются в логах nginx, докера, очередях и дампах.

## 5. Что остаётся за заказчиком

Это не наша зона ответственности, и мы этого не делали:

- роли: заказчик — оператор, исполнитель — обработчик по поручению; нужен договор
  или поручение на обработку;
- политика обработки ПДн и уведомление Роскомнадзора, включая упоминание Telegram
  как канала связи;
- утверждение юридической формулировки согласия — в `src/privacy/consent.py`
  лежит **рабочая** редакция, названная так прямо в комментарии;
- сроки хранения и порядок удаления по запросу субъекта;
- модель угроз и организационные меры на стороне заказчика.
