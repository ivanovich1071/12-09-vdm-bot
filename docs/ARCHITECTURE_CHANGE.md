## 0. Коротко

```text
Было:   выгрузка 1С ──ingest──► data/kb/products.jsonl ──► индекс в памяти до перезапуска

Стало:  выгрузка 1С ─► import-1c ─► diff ─► approve ─┐
        фото с сайта ─► media ──────────────────────┼─► снимок версии ─► data/kb/current ─► виджет, Telegram:
        реестр 1057 ─► norms ───────────────────────┘   versions/<версия>/   {version,        новое состояние
                                                         products.jsonl       sha256}          без перезапуска
```

- Источник истины о текущем каталоге — указатель `data/kb/current`: номер версии
  и sha256 снимка.
- Все, кто читает каталог, получают его через один резолвер.
- Процесс бота держит каталог одним неизменяемым состоянием и закрепляет его на
  время хода.
- Без указателя всё работает как раньше: рабочий `data/kb` на версии пока не
  переведён — это отдельный шаг выката (§7).

## 2. Problem

1. Прерванный `ingest` обрезал каталог бота.
2. Любая выгрузка сразу становилась каталогом бота, а D5 требует утверждения.
3. Не было ни версий, ни истории цен и исчезнувших товаров, ни отката.
4. Не было diff по позициям.
5. Новые цены были видны только после перезапуска обоих процессов (R4).
6. Каталог читали в обход одного пути: импорт, `search`, `norms`, `acts`, `media`.
7. Замена `engine.index` посреди хода смешала бы в одном ответе цены двух версий.
8. Нельзя было доказать, что утверждается именно показанное менеджеру.

## 3. Proposed — что реализовано

### 3.1 Указатель и снимки — `catalog/current.py`

```text
data/kb/
├── products.jsonl        legacy-файл: без указателя бот читает его
├── norms_1057.json       реестр 1057
├── current               указатель, JSON
├── .catalog.lock         замок применения версии
└── versions/
    ├── baseline/products.jsonl
    ├── 2026-09-13-001/products.jsonl
    └── …
```

- **Указатель:**

  ```json
  {"schema": 1, "version": "2026-09-13-001", "sha256": "…"}
  ```

  Путь к снимку выводится из номера:
  `<папка KB_PATH>/versions/<версия>/products.jsonl`. Путей в указателе нет, поэтому он
  одинаков на Windows, в Docker и на сервере. sha256 лежит в самом указателе: процессы
  бота `catalog.sqlite3` не читают.
- **Запись указателя:** временный файл рядом → `fsync` → `os.replace`. Если на Windows
  замену блокирует читатель (`PermissionError`), запись повторяется до 5 раз по 100 мс;
  чтение повторяется так же.
- **`KB_PATH`** указателем не стал: это путь к legacy-файлу, по нему находится папка
  базы знаний.
- **Номер версии:** первая — `baseline`, дальше `YYYY-MM-DD-NNN` по дате UTC. Номер
  не повторяется: занятые папки-сироты пропускаются.
- **Источники версии:** `baseline`, `1c`, `media`, `registry`, `rollback`.
- **Снимок** пишется один раз, не меняется и не удаляется.

### 3.2 Резолвер

`resolve_catalog(kb_path) → CatalogSnapshot(path, sha256, version)`:
- указателя нет — legacy-файл, `base_version = legacy:<sha256>`;
- указатель есть — снимок, если файл существует и sha256 совпадает;
- иначе `CatalogPointerError`: повреждённый снимок не отдаётся никогда.

Через резолвер читают:
- бот — `CatalogRuntime.open` в `build_engine`;
- импорт 1С — сравнение и `base_version`;
- `run.py search`, `norms`, `acts --check`;
- обход и переливка `media`;
- `ingest` — перенос фото из текущей версии;
- `/health`.

Тест `test_no_direct_catalog_readers_outside_resolver` не пропускает прямые
`load_index(`, `load_products(`, `from_path(` за пределами `catalog/repository.py`.
`sync_to_kb(` допускается только в legacy-ветке `run.py`.

### 3.3 Карточки и владельцы полей — `catalog_versions/cards.py`

- **Одна сборка** для `ingest`, diff и снимка: `apply_registry`,
  `carry_over_collected`, `assemble_import`. `build_kb` вызывает эти же функции и
  пишет файл через временный.
- **Владельцы полей:**

  | Владелец | Поля |
  |---|---|
  | служебные | `updated_at`, `sources` — в сравнении не участвуют |
  | страницы сайта (`media`) | `images`, `attributes` |
  | нормы (`registry`) | `norms` — ссылки из дерева выгрузки и из реестра |
  | выгрузка 1С | остальные поля |

- **Правка чужих полей запрещена.** `forbidden_changes` не даёт версиям `media` и
  `registry` менять чужие поля и набор товаров.
- **Проверки снимка.** `validate_records`: коды есть и уникальны, названия есть,
  каждая строка читается как `Product`. `--force` эти проверки не отменяет.

### 3.4 Diff — `catalog_import/diff.py`

- **Что сравнивается.** Карточка, собранная из импорта, реестра 1057 и фото
  текущего снимка, против карточки снимка — все поля, кроме служебных. Для
  сопоставления строится `ProductListRepository` без поискового индекса.
- **Статусы:**

  | `diff_status` | Счётчик | Когда |
  |---|---|---|
  | `NEW` | NEW | кода нет в текущем каталоге |
  | `NEW` + `recoding` | RECODING | новый код с одним кандидатом среди исчезнувших |
  | `AMBIGUOUS` | AMBIGUOUS | новый код, несколько кандидатов среди исчезнувших |
  | `UPDATED` | UPDATED | изменилось хотя бы одно сравниваемое поле |
  | `UNCHANGED` | UNCHANGED | поля те же; сюда же существующий код с ошибкой строки (`row_error`) |
  | `REMOVED` (состояние `MISSING`) | MISSING | код есть в каталоге, в файле нет |

- **Цена:**
  - `UNCHANGED` / `INCREASED` / `DECREASED` / `NEW` / `REMOVED`;
  - разница в рублях, процент с двумя знаками;
  - при прежней цене 0 процента нет.
- **Остаток:** `old_stock`, `new_stock`, `stock_changed`.
- **Отметки:** `needs_review`, `recoding`, `row_error`, `returning`. Вернувшийся код
  определяется по открытой строке `REMOVED` в `product_versions`.
- **Сопоставление — по D10:** существующий код проверяется только парой «код →
  товар», новый ищется только среди исчезнувших, автоматического связывания нет.
- **Отпечаток** — sha256 канонического JSON: sha256 базового снимка, sha256 реестра
  1057 и строки diff, отсортированные по коду.
- **Команды.** `import-1c --diff ID [--filter …] [--limit N]` показывает diff;
  фильтры: `price-up`, `price-down`, `new`, `removed`, `updated`, `stock`, `review`,
  `recoding`, `errors`. `import-1c --rediff ID` пересчитывает diff против текущей
  версии и заменяет строки, базовую версию и отпечаток.

### 3.5 Хранение — миграции `0002` и `0003`

Стиль `0001`: даты — TEXT ISO UTC, флаги — INTEGER, JSON — TEXT, без CHECK. SQL
только в репозиториях (D4).

- **`0002_catalog_diff`:**
  - `catalog_matches`, PK `(import_id TEXT, sku_1c)`: состояние, статус, изменившиеся
    поля, прежние и новые название, цена и остаток, разница цены, результат
    сопоставления (`match_status`, `match_method`, `match_confidence`,
    `matched_product_id`, `candidates`, `reason_codes`), отметки. Столбец отметки
    «код вернулся» — `is_returning`: `returning` — ключевое слово SQLite;
  - в `catalog_imports` добавлены `base_version`, `diff_fingerprint`, `diffed_at`,
    `approved_by`, `approved_at`, `version`.
- **`0003_catalog_versions`:**
  - `catalog_versions`:
    - `version`, `parent_version`, `source`, `import_id`;
    - `status` (`READY → APPLIED | FAILED`);
    - `created_at`, `created_by`, `applied_at`, `applied_seq` — порядок применения;
    - `snapshot_path` — относительно корня проекта;
    - `sha256`, `product_count`, `counters`, `inputs`, `forced`, `error`;
  - `product_versions`:
    - `sku_1c`, `version`, `change_status` (`NEW` / `UPDATED` / `REMOVED`);
    - `valid_from`, `valid_to`, `name`, `price`, `in_stock`, `changed_fields`, `card`;
    - индекс по открытым строкам.
- **Статусы импорта:** `UPLOADED → PARSED | INVALID → APPROVED → APPLIED`, сбой —
  `FAILED` (утверждение повторяется).

### 3.6 Утверждение — `catalog approve ID [--force] [--by ИМЯ]`

Проверки по порядку:
1. импорт `PARSED` или `FAILED`, diff сохранён, указатель есть;
2. `base_version` совпадает с текущей версией. `legacy:<sha>` равна `baseline` с тем
   же sha256: `baseline` — побайтная копия legacy-файла;
3. diff и кандидат пересчитываются, отпечаток должен совпасть с сохранённым. Иначе
   отказ и `--rediff`;
4. проверки снимка, которые `--force` не отменяет;
5. пороги: `CATALOG_MAX_REMOVED_SHARE` = 0,10, `CATALOG_MAX_PRICE_CHANGED_SHARE` = 0,30.
   Без `--force` — `SafetyCheckFailed`; с `--force` версия получает `forced = 1`.

Ошибки строк утверждение не блокируют. Существующий код применяется целиком.

### 3.7 Применение — `catalog_versions/service.py`

```text
CatalogApplyLock (замок файла средствами ОС)
  → проверка: указатель на родителе
  → снимок в versions/.building-<uuid>/, fsync, sha256 → переименование в versions/<версия>/
  → транзакция: версия READY, импорт APPROVED
  → замена указателя
  → транзакция: история товаров, версия APPLIED, импорт APPLIED
снятие замка
```

- **Замок.** `msvcrt.locking` на Windows, `fcntl.flock` на Linux; если процесс
  упал, ОС снимает замок сама. Ожидание — до 60 с, дальше `CatalogLockTimeout`.
- **Транзакции SQLite** держатся только над записью в базу, не над файлами.
- **История** считается из двух снимков (`product_changes`), а не из сохранённого
  diff.
- **Сбой записи указателя внутри процесса** переводит версию и импорт в `FAILED`.

### 3.8 Восстановление — перед каждой пишущей командой и `catalog recover`

| Случай | Что видно | Что делается |
|---|---|---|
| — | `versions/.building-*` | папка удаляется |
| A | версия `READY`, указатель на родителе, снимок цел | применение продолжается: указатель, история, `APPLIED` |
| B | версия `READY` под указателем | история из снимков родителя и версии, `APPLIED`; повтор ничего не дублирует |
| C | указатель на версии, которой нет в базе | отказ: каталог не меняется. Бот работает, только если снимок цел (иначе не стартует) |
| D | `READY`, снимка нет | `FAILED`, импорт `FAILED`, ничего не применяется |
| E | `READY`, sha256 не совпадает | `FAILED`, ничего не применяется |
| F | папка версии без записи в базе | не используется; `catalog check` о ней сообщает, номер пропускается |
| G | последняя `APPLIED` не совпадает с указателем | указатель сверяется с последней применённой версией; новая версия не создаётся |

Если указатель смотрит на повреждённый снимок, резолвер и восстановление
отказывают. `catalog check` показывает состояние, ничего не меняя.

### 3.9 Откат — `catalog rollback ВЕРСИЯ [--force]`

- Создаётся новая версия — побайтная копия снимка выбранной: источник
  `rollback`, родитель — текущая, `inputs.rollback_to` — выбранная.
- Указатель назад не переводится.
- Пороги и проверки те же, что при утверждении.
- Откат возвращает и фото той версии; собранное позже вернёт `media --sync`.

### 3.10 Состояние каталога в процессе — `catalog/runtime.py`

- **`CatalogRuntimeState`** (frozen): `index`, `catalog`, `roots`, `version`, `sha256`,
  `snapshot_path`. Строится целиком и заменяется одним присваиванием.
- **`CatalogRuntime`:**
  - `state` — закреплённое за ходом состояние (`ContextVar`), а вне хода — текущее;
  - `turn()` — закрепление; вложенный вызов закрепление не меняет;
  - `refresh()` — перед каждым ходом сверяет указатель; новая версия строится в
    фоновом потоке, ход обслуживает прежнее состояние;
  - одновременно идёт одна сборка;
  - если сборка упала, прежнее состояние остаётся, и та же пара «версия, sha256»
    повторно не собирается;
  - `start_watching(CATALOG_RELOAD_SECONDS)` — фоновая сверка для виджета и Telegram.
- **Движок:**
  - `start`, `handle_text`, `handle_action` работают внутри `runtime.turn()`;
  - `engine.index` — свойство с присваиванием;
  - `engine.catalog`, `engine.roots`, `engine.catalog_version` берутся из состояния.
- **Старт.** `build_engine(..., watch_catalog)` строит состояние синхронно,
  повреждённый указатель останавливает старт. Фоновая сверка включается для
  долгоживущих каналов.
- **Веб.** `/health` отдаёт `catalog_version` и `catalog_sha256`; `/media` берёт одно
  состояние на запрос.

### 3.11 Старые команды

- **`run.py ingest`:**
  - указатель есть — отказ с подсказкой `import-1c` → `--diff` → `catalog approve`;
  - `--legacy` пересобирает только legacy-файл, фото переносит из текущей версии,
    бот этот файл не читает;
  - без указателя — как раньше, но запись через временный файл;
  - реестр берётся из папки `--out`.
- **`run.py media` (обход, `--dedupe`, `--sync`):**
  - без указателя — прежний `sync_to_kb`;
  - с указателем — `publish_media`: без изменений версия не создаётся, иначе версия
    `media`, в которой меняются только фото и характеристики.
- **`run.py norms --source`:**
  - реестр сохраняется в папку `KB_PATH`;
  - с указателем — `publish_registry`: снятие ссылок `registry` и повторное
    применение реестра; меняются только `norms`.
- **`docker-compose.yml`:** сервис `ingest` заменён сервисом команд `catalog`
  (`profiles: tools`).

## 4. Reason

| Решение | Почему | Что отвергнуто |
|---|---|---|
| Снимок-файл и указатель (Р2, D5) | индекс, поиск, агент и 519 прежних тестов не меняются | каталог из таблиц |
| Указатель `{schema, version, sha256}` | бот сверяет снимок без базы; путь выводится из номера и не зависит от ОС | только номер версии; путь в указателе |
| Один резолвер | иначе команды молча читали бы старый файл | правка каждого места |
| Diff по собранной карточке | фото и реестр не дают ложный `UPDATED` | сравнение сырого импорта со снимком |
| `base_version` и отпечаток | ловят и смену версии, и смену реестра или фото | одна из проверок |
| Замок ОС на применение | снимается при падении процесса; транзакция SQLite не держится над файлами | `BEGIN IMMEDIATE` на всё применение; файл-флаг без замка ОС |
| История из двух снимков | одинаково работает для всех источников и при восстановлении | восстановление по сохранённому diff |
| Одно состояние и закрепление на ход | ход агента длится минуты | замена `engine.index` и сброс кэшей |
| Сверка перед ходом и фоновый поток | первый ответ после паузы уже по новой версии, ход не ждёт сборку | только сверка при сообщении или только таймер |
| Откат новой версией | линейная история | перевод указателя назад |
| `media` и `registry` без утверждения, со структурным запретом | не коммерческие данные 1С | утверждение каждого обновления фото |
| Отдельные `0002` и `0003` | применённую миграцию не правят | одна миграция |

## 7. Migration — выкат

1. **Код выкатывается без указателя:** поведение прежнее. Миграции `0002` и `0003`
   применяются при первом открытии `catalog.sqlite3`.
2. **Импорты, загруженные до EPIC 4,** diff не имеют: `import-1c --rediff ID`.
3. **`python run.py catalog init` в тихое время:**
   - побайтная копия `products.jsonl` становится `baseline`;
   - история всех товаров;
   - указатель.
4. **Процессы подхватывают `baseline`** без перезапуска; `/health` показывает
   `catalog_version`.
5. **Дальше:**
   - выгрузки — только `import-1c --file` → `--diff` → `catalog approve`;
   - фото — `media --sync`;
   - реестр — `norms`.
6. **Перед продом** — замер памяти на ВМ Cloud.ru.

На 13.09.2026 рабочий `data/kb` разработки на версии **не переведён**: `catalog init`
выполнялся только на копиях во временной папке.

## 9. Rollback — отказ от изменения

- **До `catalog init`:** вернуть код. Таблицы `0002` и `0003` старому коду не мешают.
- **После `catalog init`:**
  1. остановить виджет и Telegram;
  2. скопировать снимок текущей версии в `data/kb/products.jsonl`;
  3. удалить `data/kb/current`;
  4. вернуть код и запустить процессы.
- Снимки, история и таблицы остаются на диске, миграции только добавляли.
- Откат одной неудачной версии — `catalog rollback`, а не отказ от архитектуры.

## Уточнено при реализации (против редакции утверждения 13.09)

- Указатель — `{"schema": 1, "version", "sha256"}`: путь к снимку выводится из номера.
- Источник версии импорта называется `1c`, а не `import`.
- Сериализацию применения даёт замок ОС (`CatalogApplyLock`), а не короткая
  транзакция `BEGIN IMMEDIATE`. Транзакции SQLite — только над записью в базу.
- Восстановление A продолжает применение READY-версии, а не отменяет её. D, E —
  `FAILED`; F — сирота не используется; G — сверка указателя с базой.
- `snapshot_path` в базе — относительно корня проекта.
- Указатель сверяется перед каждым ходом и фоновым потоком.
- Добавлены `catalog check`, `catalog recover`, `catalog history`.
- Столбец отметки «код вернулся» — `is_returning` (`returning` — ключевое слово SQLite).
- Сервис `ingest` в `docker-compose.yml` заменён сервисом команд `catalog`.
- `ingest` берёт реестр из папки `--out`, а фото — из текущей версии.
