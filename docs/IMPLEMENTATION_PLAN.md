### 6.1 Diff — `catalog_import/diff.py`

- **База сравнения** — текущий утверждённый снимок, ключ — код 1С. Против
  какой версии посчитан diff, записывается у импорта (`base_version`).
- **Статусы позиции:**

  | Статус | Когда |
  |---|---|
  | `NEW` | кода нет в текущем снимке |
  | `UPDATED` | код есть, изменилось хотя бы одно поле из выгрузки |
  | `UNCHANGED` | код есть, поля из выгрузки те же |
  | `REMOVED` | код есть в снимке, в файле его нет |
  | `AMBIGUOUS` | новый код, несколько кандидатов среди исчезнувших кодов |

  `NOT_MATCHED` в импорте 1С не используется: код в строке есть всегда. Этот
  статус нужен для заказов клиентов (EPIC 9).
- **Поля из выгрузки:** название, цена, остаток, описание, состав комплекта,
  размещения, ссылки на сайт, ID Битрикса, нормативные ссылки.
  - Служебные `updated_at` и `sources` не сравниваются: иначе каждый импорт
    менял бы все товары.
  - Фото и характеристики приходят с сайта и в diff импорта не участвуют.
  - У `UPDATED` хранится список изменившихся полей. Сравниваются все поля, а
    не только цена и название: иначе смена ссылки или комплекта не попала бы
    в историю.
- **Цена:** `price_status` — `UNCHANGED` / `INCREASED` / `DECREASED` / `NEW` /
  `REMOVED`, `price_delta` в рублях и `price_delta_pct` с двумя знаками.
  - У существующего товара `NEW` — цена появилась, `REMOVED` — цена снята
    («по запросу»). Разницы в этих случаях нет.
  - Прежняя цена 0 — процента нет.
- **Остаток:** прежний и новый; отметка «изменилось наличие» при смене
  `AVAILABLE` / `NOT_AVAILABLE` / `UNKNOWN`.
- **Отметки позиции:**
  - `needs_review` — существующий код с `MATCHED_REVIEW` (например, в
    названии изменились числа);
  - `recoding` — новый код с одним кандидатом среди исчезнувших
    (`MATCHED_HIGH` или `MATCHED_REVIEW`); при нескольких — статус `AMBIGUOUS`;
  - `row_error` — строка существующего товара исключена ошибкой: статус
    `UNCHANGED`, в каталоге остаются прежние данные;
  - `returning` — код уже был в каталоге раньше: в `product_versions` есть его
    закрытая история.
- **Новый код со строкой-ошибкой** в diff не попадает — в импорт он не принят.
  Его код не считается исчезнувшим (как и в EPIC 2–3).

### 6.2 Хранение — миграция `0002`

- **`catalog_matches`** — строка на каждую позицию импорта, включая `REMOVED`:
  - состояние по коду (`EXISTING` / `NEW` / `MISSING`), статус diff, отметки;
  - прежние и новые название, цена, остаток; изменение цены; изменившиеся поля;
  - результат сопоставления: статус, способ, сходство, товар, кандидаты, коды
    причин.
- **Diff сохраняется при загрузке файла**, в одной транзакции с товарами
  импорта. Утверждается ровно то, что сохранено и показано менеджеру.
- **`base_version` у импорта** — номер версии, а пока версий нет —
  `legacy:<sha256 products.jsonl>`.
  - Если к утверждению текущая версия другая, утверждение отказывает:
    `run.py import-1c --rediff ID` пересчитывает diff, и его смотрят заново.
  - Снимок `baseline` — побайтная копия `products.jsonl`, поэтому diff,
    посчитанный до `catalog init`, после неё остаётся действительным.
- **`catalog_versions`:**
  - номер вида `2026-09-12-001`;
  - источник `baseline` / `import` / `media` / `rollback`; импорт; родительская
    версия;
  - кто утвердил, когда создана и когда применена;
  - статус `READY` → `APPLIED` | `FAILED`;
  - счётчики, путь и sha256 снимка, число товаров.
- **`product_versions`** — строка только на изменённый товар:
  - код, версия, `valid_from`, `valid_to`, статус изменения (`NEW` /
    `UPDATED` / `REMOVED`), название, цена, остаток, карточка целиком (JSON);
  - при изменении у прежней строки закрывается `valid_to` — это и есть история
    цены;
  - исчезнувший товар получает строку `REMOVED` с последней карточкой: история
    и карточка не удаляются;
  - `baseline` записывает все товары.

### 6.3 Снимок и указатель

- **Снимок** — `data/kb/versions/<версия>/products.jsonl`. Пишется через
  временный файл, после записи считается sha256. Снимки не изменяются и не
  удаляются.
- **Указатель** — файл `data/kb/current` рядом с `KB_PATH`, внутри номер
  версии. Замена через временный файл и `os.replace`. Символические ссылки не
  используются: на Windows они ненадёжны.
- **Указатель — единственный источник того, какая версия текущая.**
- **Совместимость.** Указателя нет — бот читает `KB_PATH` (`products.jsonl`),
  как сейчас; тесты и разработка не меняются.
- **Указатель есть, а снимка нет или sha256 не совпадает:** процесс при старте
  останавливается с понятной ошибкой; работающий процесс оставляет прежний
  индекс и пишет ошибку в журнал. Неверные цены хуже остановки.
- **Состав снимка при утверждении импорта:**
  - товары импорта — коммерческие поля и описание из выгрузки;
  - существующие товары со строкой-ошибкой — из текущего снимка без изменений;
  - реестр 1057 — `_apply_registry`;
  - фото и характеристики — из текущего снимка, `_carry_over_collected`;
  - `REMOVED` в снимок не попадают. Вариант «оставить с `is_active=false`» не
    выбран: тогда поиск и агент везде должны пропускать неактивные.

  Порядок — как в файле, оставленные товары — в конце по коду. Контрольный
  тест: снимок и `run.py ingest` на одной выгрузке совпадают, кроме
  `updated_at`.
- **Первая версия — `baseline`:** `run.py catalog init` копирует нынешний
  `products.jsonl` в снимок, записывает историю всех товаров и ставит
  указатель. Команда разовая: при существующих версиях отказывает.

### 6.4 Утверждение и применение

- **`run.py catalog approve ID [--force] [--by ИМЯ]`.** Статусы импорта
  `PARSED` → `APPROVED` → `APPLIED`; сбой сборки снимка — `FAILED` с причиной,
  `approve` можно повторить.
- **Порядок шагов:**
  1. проверки: версии есть, `base_version` равна текущей, пороги;
  2. сборка снимка во временный файл → `versions/<версия>/products.jsonl`,
     sha256;
  3. запись версии со статусом `READY`, импорт `APPROVED`;
  4. переключение указателя;
  5. одна транзакция: `product_versions`, версия `APPLIED`, импорт `APPLIED`.
- **Восстановление после сбоя:**
  - прервалось до шага 4 — версия `READY` без указателя, бот не менялся,
    `approve` повторяется;
  - прервалось между шагами 4 и 5 — указатель уже на новой версии. Любая
    команда `catalog` видит под указателем версию `READY` и дописывает шаг 5
    по сохранённому diff.
- **Одновременно применяется одна версия:** запись в `catalog_versions` под
  блокировкой SQLite (`BEGIN IMMEDIATE`).
- **Ошибки строк утверждение не блокируют** — см. отметку `row_error`.
- **Существующий код применяется целиком**, в том числе с `needs_review`: 1С —
  источник истины для цены и остатка, код уникален (D8). Предупреждение видно
  в diff.
- **Перекодировка автоматически не связывается.** Товар применяется как `NEW`,
  старый код — как `REMOVED`. Связь, перенос фото и истории — вручную в EPIC 5.
  До этого у перекодированного товара нет фото: они привязаны к коду.
  Блокировать утверждение до разбора перекодировок не стали — обновления
  каталога встали бы до EPIC 5.
- **Защита от обрезанного или сдвинутого файла** — без `--force` утверждение
  отказывает, если:
  - исчезает больше `CATALOG_MAX_REMOVED_SHARE` = 10 % товаров текущей версии;
  - цена меняется больше чем у `CATALOG_MAX_PRICE_CHANGED_SHARE` = 30 %
    существующих товаров (цены в копейках вместо рублей, сдвиг колонок).
- **Кто утвердил** — имя пользователя ОС или `--by`. Пользователи и роли —
  EPIC 5.

### 6.5 Откат

- `run.py catalog rollback ВЕРСИЯ` создаёт **новую** версию — копию выбранной:
  источник `rollback`, родитель — текущая. В `product_versions` пишется
  разница между текущей и выбранной, указатель переключается.
- Указатель назад не переводится: так история остаётся линейной, видно, что
  откатывали, а `valid_from` / `valid_to` не противоречат друг другу. Цена —
  ещё один снимок, около 15 МБ.
- Применяется тем же порядком шагов и с тем же восстановлением, что и `approve`.

### 6.6 Бот узнаёт о новой версии

- При обработке сообщения `DialogEngine` не чаще раза в 30 секунд читает
  указатель. Номер изменился — в фоновом потоке строится новый `CatalogIndex`
  (около 2,7 с на 5 936 товарах), затем подменяется `engine.index`,
  сбрасываются кэши `_roots` и `catalog`.
- Пока индекс строится, бот отвечает по прежнему. Одновременно строится не
  больше одного индекса.
- Снимки версий загружаются без `lru_cache`, иначе в памяти копятся старые
  индексы.
- Виджет и Telegram — отдельные процессы, каждый сверяет указатель сам.
  Сигналы и HTTP не нужны. Все обращения к каталогу — диалог, инструменты
  агента, веб — идут через `engine.index`, поэтому подмены достаточно.
- Корзина хранит цену на момент добавления, как и сейчас. Пересчёт цены в
  заказе — EPIC 10, версия каталога в заказе — EPIC 10–11.

### 6.7 Старые команды

- **`run.py ingest`:** если указатель есть, отказывает и подсказывает путь
  `import-1c` → `catalog approve`. `--legacy` — прежнее поведение для
  разработки; бот с указателем этот файл не читает. Запись `products.jsonl`
  переводится на временный файл: сейчас прерванная запись обрезает его.
- **`run.py media --sync`:** если указатель есть, создаёт версию `media` от
  текущей, где меняются только фото и характеристики, и применяет её без
  утверждения. Если ничего не изменилось, версия не создаётся. Без указателя —
  как сейчас.
- **Место на диске:** снимок около 15 МБ; при 4–5 версиях в месяц — 60–75 МБ,
  около 1 ГБ в год. Версии не удаляются (ТЗ).
