## 1. Цель

Сохранить рабочий бот `26-08-vdm-bot` и превратить его в **AI-систему
подготовки и проверки закупки образовательного оборудования**:
подбор → подготовка → проверка → актуализация.

Бот — это интерфейс. Центр системы — backend / core.

Итог v2 — два сквозных сценария:

- **A. Новый подбор.** «Нужно оснастить кабинет химии в школе по 838» →
  учреждение и кабинет → норматив → товары → первая спецификация с актуальными
  ценами → карточки и фото по запросу → уточнение → Excel/Word → корзина →
  предзаказ → менеджер.
- **B. Готовый заказ.** «Вот наш заказ из 1С/Excel» → файл → разбор →
  сопоставление товаров → текущая цена → наличие → норматив → расхождения →
  отчёт → проверенный предзаказ → менеджер.

Главный принцип ответа: не «я думаю, вам подойдёт…», а «по утверждённому
каталогу найдено…» или «в текущем каталоге соответствие не подтверждено».

## 4. Роли

**Salesman — AI Sales / Procurement Specialist.**

- Режимы: `CONSULTATION`, `SELECTION`, `SPECIFICATION`, `PRODUCT_DETAILS`,
  `OBJECTION`, `ORDER_REVIEW`, `CART`, `PREORDER`.
- Цикл хода: сообщение → intent → обновление task profile → режим →
  поиск/инструмент → проверка → ответ → обновление профиля.
- Путь подбора: DISCOVERY → SELECTION → PRESENTATION → OBJECTION → REVISION →
  SPECIFICATION → CART → PREORDER.

**Consultant** объясняет систему, нормативные документы, порядок закупки,
обработку ПДн и возможности. Он **не** подбирает товары, не формирует
спецификацию и корзину, не спрашивает бюджет и количество ради продажи, не
обсуждает наличие, не инициирует заказ и не проверяет заказ.

Явное намерение выбрать товар передаёт разговор продавцу:
CONSULTANT → SELECTION_INTENT → SALESMAN.

Загрузка файла не идёт через обычный подбор: FILE_UPLOAD → ORDER_REVIEW.

## 5. Task profile и сброс

Состояние задачи хранится отдельно от истории. Расширяется существующий
`DialogProfile`, параллельная система состояния не создаётся.

Минимальный набор полей: `institution_type`, `institution_name`, `room`,
`zone`, `grade`, `age_group`, `goal`, `norm_document`, `norm_item`, `budget`,
`deadline`, `quantity`, `preferences`, `selected_products`,
`rejected_products`, `shown_products`, `objections`, `offer`, `stage`.

**`/start`** сбрасывает текущую задачу, этап и подбор. Он не удаляет историю,
прежние заказы, документы, аудит и пользователя.

## 6. Нормативы

- **838** — школы, общее образование. **1057** — дошкольное образование.
  Прочие документы — через общий norm engine. Автоматически подменять один
  документ другим нельзя.
- Цепочка: **DOCUMENT → POINT → CATEGORY → PRODUCT MAPPING**. LLM не
  придумывает связь «пункт → товар». Нет соответствия в данных →
  `REVIEW_REQUIRED`.
- Проверка заказа по норме: `NORM_OK` / `NORM_MISMATCH` / `NORM_UNKNOWN` /
  `REVIEW_REQUIRED`. Юридическое заключение не выдаётся.
- **Количество всегда с источником:** `norm`, `user`, `calculated`,
  `default`, `manager`. Рассчитанное или количество по умолчанию нельзя
  выдавать за нормативное.

## 7. Подбор, поиск, карточки

- **Первый проход:** минимум вопросов. «Школа + кабинет информатики» —
  достаточно, чтобы искать. Количество учеников, бюджет и срок уточняются
  после первого результата.
- **Первая спецификация** показывает позицию, артикул, название, цену,
  количество и сумму — если цена известна из актуального источника.
- **Поиск:** QUERY → candidate retrieval → hard filters → ranking → top N.
  Жёсткие фильтры: `institution_type`, `room`, `zone`, `norm`, `category`,
  `age_group`, `availability`, `price`. Запрос про кабинет информатики не
  должен приносить товары из дошкольного, профессионального, химии и других
  чужих разделов.
- **Карточка:** название, артикул, цена, наличие, описание, характеристики,
  фото, URL, нормативные связи. У каждого поля свой источник.
- **Пагинация:** 3 товара и кнопка «Показать ещё». Без повторов, без выдачи
  по 20 штук, без выдуманных карточек.

## 8. Источники истины

| Данные | Источник |
|---|---|
| Цена, наличие, остаток, артикул, единица, коммерческий статус | утверждённый каталог из 1С |
| Карточка: описание, характеристики, фото, URL | источник карточек сайта — сейчас Bitrix |
| Нормативы, пояснения, правила, маппинги, FAQ | нормативная KB |
| Состояние системы, заказы, предзаказы, версии | backend DB |
| AI-интерпретация | **не источник истины** |

Абстракции источников: `CatalogSource`, `CardSource`, `CRMAdapter`,
`NotificationChannel`. Tilda на текущем этапе не используется (D1).

## 9. Импорт 1С

- **Модуль `src/catalog_import/`:** `models`, `parser`, `validator`,
  `normalizer`, `matcher`, `diff`, `snapshots`, `importer`, `service`.
- **Конвейер:** UPLOAD → HASH → PARSE → VALIDATE → NORMALIZE → MATCH → DIFF →
  PREVIEW → ADMIN APPROVE → APPLY. Загрузка сама по себе каталог бота **не
  меняет**.
- **Предпросмотр:** всего строк; новые, изменённые, без изменений,
  исчезнувшие; exact match, high confidence, review required, not found,
  ambiguous. Только реальные числа.
- **Diff по позиции:** `article`, `old_name`, `new_name`, `old_price`,
  `new_price`, `price_delta`, `old_stock`, `new_stock`, `match_method`,
  `confidence`, `status`.
  - Статусы: `NEW` / `UPDATED` / `UNCHANGED` / `REMOVED` / `AMBIGUOUS` /
    `NOT_MATCHED`.
  - Цена: `UNCHANGED` / `INCREASED` / `DECREASED` / `NEW` / `REMOVED`, плюс
    изменение в процентах.
- **Порядок сопоставления:** код 1С → SKU → точное название → нормализованное
  название → производитель → характеристики → размеры → fuzzy → AI-assisted →
  ручная проверка.
  - Статусы: `MATCHED_EXACT` / `MATCHED_HIGH` / `MATCHED_REVIEW` / `NOT_FOUND`
    / `AMBIGUOUS`.
  - Порог настраивается; ниже порога → `MANUAL_REVIEW`. AI может предложить
    соответствие, но не утверждает неоднозначное.
- **Версии:** каждое утверждение создаёт `catalog_version` (например
  `2026-09-12-001`): файл, кто и когда загрузил, строк, создано, обновлено,
  удалено, неоднозначных, время утверждения.
  - `product_version` хранит `valid_from` / `valid_to` и источник.
  - Старые версии не удаляются, откат возможен.
- **Снимок:** `data/kb/versions/<версия>/products.jsonl`, указатель
  `data/kb/current` переключается атомарно. Бот читает только текущий
  утверждённый снимок, индекс обновляется без перезапуска, если архитектура
  позволяет.
- **Исчезнувший товар:** `REMOVED` / `MISSING_FROM_SOURCE`. История и карточка
  не удаляются.
- **Фото** при смене цены заново не скачиваются. Коммерческие данные и медиа
  разделены.

## 10. Web Admin

- Разделы: Dashboard; Catalog (Current, Import, Diff, Matching, Versions);
  Orders (Incoming, Preorders, Review, History); Norms (838, 1057, Other);
  Knowledge Base; Users; Integrations; Audit; System.
- **ADMIN:** пользователи, настройки, импорт, интеграции. **MANAGER:** заказы,
  предзаказы, проверка сопоставлений, просмотр, подтверждение.
- **Импорт по шагам:** файл → проверка → сопоставление → изменения → требуют
  решения → подтверждение → применение.
- **Ручное сопоставление:** строка из 1С против карточек A / B / C, кнопки
  «Выбрать» и «Не сопоставлять».
- **Фильтры изменений:** цена ↑, цена ↓, новые, исчезнувшие, изменено наличие,
  не сопоставлено, требует проверки.
- **Технология:** FastAPI + Jinja2 + htmx, без SPA. Основной инструмент
  менеджера — браузер, а не Telegram. Web Admin ≠ Mini App: права и интерфейсы
  не смешиваются.

## 11. Заказ клиента, предзаказ, менеджер

- **Форматы:** Excel и CSV — сначала; Word и PDF — отдельными парсерами по
  реальным образцам.
- **Поток:** файл → парсер → нормализация → позиции → сопоставление → текущий
  каталог → проверка.
- **Позиция заказа:** `source_line`, `source_article`, `source_name`,
  `quantity`, `matched_product_id`, `match_status`, `confidence`,
  `current_price`, `price_status`, `availability`, `norm_status`.
  Отсутствующее не выдумывается (`quantity = UNKNOWN`), уточняется только
  необходимое.
- **Проверки:**
  - цена — `PRICE_OK` / `PRICE_CHANGED` / `PRICE_NOT_FOUND`;
  - наличие — `AVAILABLE` / `NOT_AVAILABLE` / `UNKNOWN`, и `UNKNOWN` никогда
    не превращается в `AVAILABLE`.
- **Итоговый отчёт:** проверено, совпало, изменена цена, не найдено,
  неоднозначно, нет наличия, требуют проверки нормы. Все числа считает
  программа.
- **Предзаказ:** `DRAFT` → `IMPORTED` → `MATCHED` → `PRICE_CHECKED` →
  `READY_FOR_MANAGER` → `SENT_TO_MANAGER` → `MANAGER_REVIEW` → `CONFIRMED` /
  `REJECTED`.
  - До подтверждения менеджером это не заказ.
  - Не обещать наличие, резерв, доставку, скидку, срок и окончательную цену
    без подтверждения источником.
- **Менеджер получает:** клиента, организацию, контакт, исходный файл,
  распознанные и сопоставленные позиции, актуальные цены, наличие,
  расхождения, норматив, комментарии.
- **Уведомления** через адаптеры: CRM, Email, Telegram, MAX. Сбой отправки →
  предзаказ сохранён, `notification = FAILED`, повтор.
- **CRM** — цель интеграции, а не источник истины. Её логика не проникает в
  ядро.

## 12. Документы

- Модуль `src/documents/`: `specification`, `excel_generator`,
  `word_generator`, `pdf_generator`, `validators`, `templates/`.
- Никогда «LLM → готовый Excel». Только: AI → структурированные данные →

- **Предварительная спецификация клиенту:** организация, учреждение, кабинет,
  норматив, позиции (артикул, наименование, количество, цена, сумма), итого,
  комментарий.
- **Отчёт менеджеру:** исходная позиция, сопоставленная позиция, артикул, цена
  в файле, текущая цена, наличие, норматив, расхождение, комментарий.

## 13. База знаний (Obsidian)

- Структура `VDM_KB/`: `norms/{838,1057,other}`, `mappings`, `rules`, `faq`,
  `explanations`, `metadata`.
- В Obsidian **не хранятся** как источник истины цены, остатки, наличие,
  коммерческое состояние, заказы и данные клиентов.
- На сервере Obsidian.exe не нужен. Поток: vault → Markdown → KB Importer →
  проверка → индекс → RAG / norm engine.
- При передаче заказчику описать: где vault, как править, как публиковать, как
  проверяется, как переиндексировать, как бэкапить.

## 16. AI и детерминированный слой

- **LLM может:** понять запрос, определить intent, извлечь параметры,
  объяснить, предложить, переформулировать, помочь с сопоставлением.
- **LLM не устанавливает:** товар, артикул, цену, наличие, скидку, срок,
  доставку, резерв, норматив, пункт нормы, юридическое соответствие, итог
  заказа. Нет данных → `UNKNOWN` или `REVIEW_REQUIRED`.
- **Бэкенд считает сам:** цену, количество × цену, итог, изменение цены,
  статус сопоставления, версию каталога, статусы заказа, нормы и наличия.
- **Промпты** не содержат бизнес-истину. Слой промптов изолирован и
  заменяется без изменения логики (D2).

## 18. Порядок работы

- **Каждый EPIC:** ANALYZE → REPORT → APPROVE → IMPLEMENT → TEST → REGRESSION
  → RUFF → DOCUMENT → COMMIT → STOP. Следующий EPIC — только по отдельной
  команде.
- **Без big bang:** 1С, CRM, админка, Mini App, MAX, Obsidian и заказы одним
  проходом не делаются.
- **Definition of Done:** реализация + тесты + регрессия + документация + нет
  секретов + ruff + все существующие тесты.
- **Тесты сломались:** остановить рефакторинг, найти причину, исправить,
  повторить. Отключать тесты нельзя.
- **Меняется существующая архитектура:** сначала `ARCHITECTURE_CHANGE.md` —
  Current, Problem, Proposed, Reason, Affected files, Risks, Migration, Tests,
  Rollback.
- **Неопределённость:** DO NOT GUESS. Искать в коде, конфигурации и
  документах, отмечать `UNKNOWN`, предлагать варианты.
- **Приоритеты:** STABILITY > DATA CORRECTNESS > DETERMINISTIC VALIDATION >
  BACKWARD COMPATIBILITY > FEATURES > REFACTORING.
