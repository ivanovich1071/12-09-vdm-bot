# Запуск проекта в VS Code

Инструкция для чистой машины с Windows 10 или 11: от установки Python до
работающего Telegram-бота, Core API и Mini App. Проверено на Windows 10 и
Python 3.13.4.

Секретов в этом файле нет и не будет: токены и ключи вписываются только в `.env`
на вашей машине.

**Порядок запуска одним взглядом**

```text
Под VPN РФ, полный порядок — §0:
1. python -m pytest -q                         тесты, 2–3 минуты
2. python run.py site                          каталог с сайта → data\raw\site-ДАТА.xlsx
3. python run.py catalog init                  один раз
4. python run.py import-1c --file <книга>      на проверку, печатает ID
5. python run.py catalog approve <ID>          каталог бота обновлён
6. python run.py media --in-stock / --sync     фото и характеристики
7. python run.py telegram --check              токен, webhook, модель

TERMINAL 1  python run.py widget        Core API + Mini App на http://127.0.0.1:8000 (Mini App — позже)
TERMINAL 2  python run.py telegram      Telegram-бот
```

Оба терминала — с активированным окружением `.venv` (§4).

## 0. Запуск под VPN РФ — все команды по порядку

VPN с российским адресом нужен для двух вещей: с машины вне РФ не открывается
vdm.ru (фотографии и характеристики товаров) и недоступна модель Cloud.ru. Mini App
на этом этапе не запускаем — только бот.

**Откуда что берётся.** Выгрузок 1С не будет — каталог собирается с сайта vdm.ru
(шаг 3): код 1С, название, адрес, цена, остаток, разделы и описание. Остаток на сайте тот
же, что был в выгрузке 1С («в наличии» — число, «под заказ» — 0). Парсер собирает книгу в
формате прежней выгрузки, и она проходит обычный импорт с проверками, diff и порогами —
каталог бота меняется только после `catalog approve`. Фотографии и характеристики — шаг 4.

**TERMINAL 1 — подготовка.** Включите VPN РФ, затем:

```powershell
.\.venv\Scripts\Activate.ps1
```

```powershell
chcp 65001
```

1. Сайт виден из окружения проекта — ожидаемо `200`:

   ```powershell
   python -c "import urllib.request; print(urllib.request.urlopen('https://vdm.ru/', timeout=10).status)"
   ```

2. Тесты — ожидаемо `828 passed`, без сети. Идут 2–3 минуты и первые полминуты ничего
   не печатают — не прерывайте:

   ```powershell
   python -m pytest -q
   ```

3. **Каталог с сайта** — цены, остатки, названия, разделы. Сначала проба на небольшом
   разделе, книга не пишется:

   ```powershell
   python run.py site --root https://vdm.ru/catalog/oborudovanie_dlya_detskogo_sada/10_patrioticheskoe_vospitanie/ --limit-sections 2
   ```

   Весь каталог — около 300–400 страниц, на медленном сайте час-полтора. `Ctrl+C`
   сохраняет загруженное, повторный запуск продолжает с места остановки (файл обхода
   живёт 12 часов, дальше обход начинается заново — цены устарели):

   ```powershell
   python run.py site
   ```

   В конце команда печатает путь к книге `data\raw\site-ДАТА-ВРЕМЯ.xlsx`, сколько товаров
   новых и сколько пропало с сайта, и следующие команды. Если какие-то страницы не
   загрузились, книга не собирается — запустите `python run.py site` ещё раз.

   Один раз, если каталог ещё не ведётся версиями (команда `site` об этом напишет):

   ```powershell
   python run.py catalog init
   ```

   Импорт книги на проверку — каталог бота не меняется, печатается ID импорта и что
   изменится (цены, остатки, новые, исчезнувшие):

   ```powershell
   python run.py import-1c --file data\raw\site-ДАТА-ВРЕМЯ.xlsx
   ```

   Утверждение — бот подхватывает новую версию без перезапуска:

   ```powershell
   python run.py catalog approve ID
   ```

   Если импорт сообщил о превышении порогов (исчезает больше 10 % каталога или цена
   меняется больше чем у 30 %), сначала посмотрите изменения —
   `python run.py import-1c --diff ID` — и только если всё верно, утвердите с `--force`.

4. Фотографии и карточки с сайта. Проба на 20 карточках — полминуты:

   ```powershell
   python run.py media --cards 20
   ```

   Весь каталог — несколько часов: сайт отвечает медленно, по 2–4 секунды на карточку.
   `Ctrl+C` сохраняет собранное, повторный запуск продолжает с места остановки, уже
   собранные карточки к сайту не обращаются:

   ```powershell
   python run.py media
   ```

   Быстрее — сначала только товары в наличии:

   ```powershell
   python run.py media --in-stock
   ```

   Несколько файлов в папке товара — это разные кадры галереи (обложка, виды), а не
   копии. Одинаковые по байтам снимки внутри папки убирает `--dedupe`; у разных товаров
   общие фото бывают законно — например, у вариантов одного набора, — их не трогаем.
   После обхода — убрать дубли внутри папок и перелить собранное в каталог:

   ```powershell
   python run.py media --dedupe
   ```

   ```powershell
   python run.py media --sync
   ```

5. Модель: основной — Cloud.ru, запасной — OpenRouter. В `.env` одна строка
   `LLM_PROVIDER=auto` (не две: при повторе действует первая). Если Cloud.ru не отвечает,
   ход обслуживает OpenRouter, а Cloud.ru пробуется снова через 5 минут. Проверка по
   шагам — у Cloud.ru должно быть `✓ TCP 443`:

   ```powershell
   python run.py llm
   ```

6. Бот: токен, webhook, модель. Строка `[!!] Mini App` сейчас ожидаема:

   ```powershell
   python run.py telegram --check
   ```

**TERMINAL 2 — бот.** Кнопка `+` в панели терминала:

```powershell
.\.venv\Scripts\Activate.ps1
```

```powershell
python run.py telegram
```

Бот готов, когда в журнале появится `Run polling for bot @…`. В Telegram нажмите
«Начать заново» на нижней клавиатуре (или `/restart`) и подтвердите «Да, начать заново» —
бот забудет прежний разговор и очистит корзину. `/start` посреди разговора тоже сначала
спрашивает подтверждение. Одна копия бота на один токен: если бот запущен
где-то ещё, в журнале будет `TelegramConflictError` (§15).

**Проверка маршрутов** — в TERMINAL 1, после нескольких сообщений боту:

```powershell
python run.py dialogs --last 10
```

В каждом ходе: `route.role` — кто ответил, `route.intent` — намерение реплики,
`route.previous_agent` — кто отвечал до этого, `route.reason` — почему. Сценарии
проверки — §14, таблица A. В консоли бота та же информация идёт строкой
`Оркестратор: «…» → намерение …, прежний агент …, отвечает …`.

## 4. Виртуальное окружение

Создать — один раз, в папке проекта:

```powershell
python -m venv .venv
```

(или `py -3.13 -m venv .venv`, если версий несколько).

Активировать — в **каждом** новом терминале:

```powershell
.\.venv\Scripts\Activate.ps1
```

После активации в начале строки появится `(.venv)`.

**PowerShell пишет «выполнение сценариев отключено в этой системе».** Разрешите
локальные скрипты для своего пользователя — один раз:

```powershell
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
```

Если менять политику нельзя, разрешите только для текущего окна:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
```

Можно обойтись и без активации — вызывать Python окружения по полному пути:

```powershell
.\.venv\Scripts\python.exe run.py telegram --check
```

**Скажите VS Code использовать это окружение:** `Ctrl+Shift+P` →
`Python: Select Interpreter` → `.venv`. Без этого запуск по F5 и вкладка Testing
пойдут мимо окружения.

## 6. Данные каталога

Бот и Core API читают каталог из `data/kb`. В репозитории его нет: цены, остатки и
документы заказчика в git не хранятся. Без каталога процессы не стартуют
(`FileNotFoundError: data/kb/products.jsonl`).

Два пути:

- **Скопировать готовую папку `data/`** с рабочей машины — быстрее всего. Нужны как
  минимум `data/kb/` (база знаний, версии каталога, `norm_items.json`). Хранилище
  `data/vdm.sqlite3` копировать не нужно: оно создаётся само, а в чужом лежат
  корзины и контакты.
- **Собрать из выгрузки 1С** — положить `.xlsx` в `data\raw\` и выполнить:

  ```powershell
  python run.py ingest --source data\raw\<выгрузка>.xlsx
  ```

  ```powershell
  python run.py catalog init
  ```

  Реестр приказа 1057, тексты приказов и фотографии — §18.

Проверить каталог без бота:

```powershell
python run.py search "мячи для спортивного зала в наличии до 2000 руб"
```

## 7. Файл `.env`

```powershell
Copy-Item .env.example .env
```

```powershell
code .env
```

`.env.example` — шаблон без секретов, он в git. `.env` — ваши значения, в git не
попадает (`.gitignore`). Проверить:

```powershell
git check-ignore .env
```

Ответ `.env` — значит, файл игнорируется.

**Что заполнить для Telegram, модели и Core API** (остальное можно оставить как в
шаблоне):

| Переменная | Значение | Комментарий |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | токен нового бота | §8. Только в `.env`, больше нигде |
| `TELEGRAM_MINIAPP_URL` | пусто — при локальной разработке | `https://<хост>/miniapp` — после деплоя, §12 |
| `LLM_PROVIDER` | `auto` | Cloud.ru основной, при отказе — OpenRouter, §13. Строка в `.env` одна |
| `OPENROUTER_API_KEY` | ключ OpenRouter | openrouter.ai → Keys |
| `CLOUDRU_API_KEY` | ключ Cloud.ru | Нужен для `cloudru` и `auto` |
| `CORE_API_KEY` | случайная строка | Ключ серверных адаптеров Core API (`X-Core-Api-Key`). Пусто — эти маршруты отвечают 503. Боту в своём процессе не нужен |
| `CORE_MANAGER_KEY` | другая случайная строка | Ручные операции менеджера (`X-Manager-Key`). Пусто — выключены |
| `WIDGET_HOST`, `WIDGET_PORT` | `0.0.0.0`, `8000` | Адрес сервера Core API и Mini App |

**Прежнее имя `TELEGRAM_TOKEN` не используется.** Если в старом `.env` есть строка
`TELEGRAM_TOKEN=…` — удалите её: там токен прежнего бота. Бот, сервер и `--check`
предупреждают, если она осталась.

Случайный ключ для `CORE_API_KEY` и `CORE_MANAGER_KEY` удобно получить сразу в
буфер обмена, не выводя его на экран:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(32), end='')" | Set-Clipboard
```

Затем вставьте в `.env` после знака `=`.

## 8. Новый Telegram-бот через @BotFather

Бот создаётся заново. Старого бота, его токен и webhook не используйте.

1. Откройте в Telegram **@BotFather** — официальный бот Telegram, с синей галочкой.
2. Отправьте команду `/newbot`.
3. Укажите **название** — его видят пользователи в заголовке чата, например
   «ЭЛТИ-КУДИЦ консультант».
4. Укажите **username** — латиницей, уникальный, обязательно оканчивается на `bot`.
5. BotFather пришлёт сообщение с **токеном** (строка после «Use this token to access
   the HTTP API»). Токен — это пароль от бота: кто его знает, тот управляет ботом.
6. Скопируйте токен и впишите **только в `.env`**, после знака `=`, без кавычек и
   пробелов:

   ```env
   TELEGRAM_BOT_TOKEN=<вставьте сюда токен из BotFather>
   ```

   Не присылайте его в чаты, не вставляйте в документы, задачи и скриншоты.
7. Убедитесь, что `.env` не попадёт в коммит:

   ```powershell
   git status --short
   ```

   В списке не должно быть `.env`.

**Если токен всё-таки засветился:** @BotFather → `/revoke` → выбрать бота → новый
токен в `.env`, перезапустить бота. Старый токен перестаёт работать сразу.

## 9. Проверка перед запуском

```powershell
python run.py telegram --check
```

Команда ничего не запускает и **не печатает токен**: проверяет, что токен задан и
принят Telegram, что у бота нет webhook, что модель настроена, и — если задан
`TELEGRAM_MINIAPP_URL` — что Mini App отвечает по этому адресу.

Ожидаемо при локальной разработке:

```text
[ok] TELEGRAM_BOT_TOKEN — задан
[ok] Модель — провайдер openrouter
[ok] Токен — бот @<username>, id <номер>
[ok] Webhook — не установлен — опрос получит сообщения
[!!] Mini App — TELEGRAM_MINIAPP_URL не задан — кнопка «Приложение» не появится
```

Строка `[!!] Mini App` локально ожидаема, из-за неё команда завершается с кодом 1.
Все остальные строки должны быть `[ok]`.

Если `TELEGRAM_MINIAPP_URL` задан, повторите `--check` **после** запуска
TERMINAL 1 (§10): проверка открывает страницу Mini App, `/api/health` и вход по
подписи Telegram.

Отдельно — модель по шагам (DNS, TCP 443, запрос, вызов инструмента):

```powershell
python run.py llm
```

## 10. Запуск: два терминала

Бот и сервер — два процесса с одним `.env` и одной папкой `data/`. Второй
терминал открывается кнопкой `+` в панели терминала VS Code.

### TERMINAL 1 — Core API и Mini App

```powershell
.\.venv\Scripts\Activate.ps1
```

```powershell
python run.py widget
```

## 11. Mini App локально

**Локальный адрес:** http://127.0.0.1:8000/miniapp — страница открывается в
браузере разработчика, пока работает TERMINAL 1. Так проверяется вёрстка и сама
страница.

**Вход под пользователем Telegram так не проверить.** Mini App входит подписанными
данными Telegram (`initData`), а в обычном браузере их нет.

**Telegram не откроет `http://127.0.0.1:8000/miniapp`** — ни у вас, ни у
пользователя:

- `127.0.0.1` — это адрес вашего собственного компьютера, с телефона и с чужого
  устройства он указывает на них самих;
- Telegram открывает Mini App только по **HTTPS**.

Поэтому бот не публикует кнопку «Приложение» для адреса без `https://` и пишет в
журнал предупреждение.

Для настоящего открытия из Telegram нужен публичный адрес:

```text
https://PUBLIC_HOST/miniapp
```

## 12. Публичный адрес Mini App и деплой на Cloud.ru

**Адрес — только настройка.** Код Mini App читает его из `.env`
(`TELEGRAM_MINIAPP_URL`, `src/core/config.py`) и больше нигде не хранит: ни в
Python, ни в HTML, ни в JS. За этим следит тест
`test_miniapp_address_lives_only_in_the_configuration`. При смене домена код не
меняется.

```text
Сейчас, локальная разработка:
    TELEGRAM_MINIAPP_URL=                         (пусто)
    страница — http://127.0.0.1:8000/miniapp, только в браузере разработчика

После деплоя на Cloud.ru:
    TELEGRAM_MINIAPP_URL=https://<cloud.ru-host>/miniapp

    Telegram → HTTPS → Cloud.ru → python run.py widget (порт 8000) → /miniapp
```

Порядок на сервере:

1. На сервере — тот же проект, `.env` и `data/`. Бот и сервер Mini App работают с
   **одним** `TELEGRAM_BOT_TOKEN`: по нему сервер проверяет подпись входа в Mini App.
2. `python run.py widget` за HTTPS-прокси (nginx, Caddy или балансировщик облака) с
   действующим сертификатом для `<cloud.ru-host>`.
3. В `.env`: `TELEGRAM_MINIAPP_URL=https://<cloud.ru-host>/miniapp`.
4. `python run.py telegram --check` — теперь и строки Mini App `[ok]`.
5. Перезапустить бота: он читает `.env` при старте и публикует кнопку «Приложение».

Для временной проверки с машины разработчика подойдёт и HTTPS-туннель к порту 8000 —
это инструмент разработчика, в приложение он не встраивается.

## 13. Модель: Cloud.ru основной, OpenRouter запасной

Провайдеров два, выбор — настройка `LLM_PROVIDER` (`src/agent/providers.py`):

| Значение | Что делает |
|---|---|
| `auto` | **Так настроено.** Сначала Cloud.ru, при отказе — OpenRouter. Сбой Cloud.ru запоминается на 5 минут: в это время ходы идут сразу в OpenRouter |
| `cloudru` | Только Cloud.ru — модель заказчика |
| `openrouter` | Только OpenRouter |

14.09 с машины разработки под VPN РФ Cloud.ru не отвечал на TCP 443 — бот работал через
OpenRouter. Когда `python run.py llm` покажет у Cloud.ru `✓ TCP 443` и ответ модели, `auto`
переключится на него сам.

Без модели бот тоже отвечает: подбор делает Procurement Core по реплике, корзина и
предзаказ работают. Разговора консультанта и продавца при этом нет.

### Проверка Cloud.ru под VPN

VPN — способ доступа разработчика к Cloud.ru. В приложении настроек VPN нет и не
будет: приложение ходит в сеть как обычно, а VPN включается на машине.

1. Включите VPN.
2. DNS:

   ```powershell
   Resolve-DnsName foundation-models.api.cloud.ru
   ```

3. TCP:

   ```powershell
   Test-NetConnection foundation-models.api.cloud.ru -Port 443
   ```

   Ожидаемо: `TcpTestSucceeded : True`.
4. TLS (раньше отказ был именно здесь — таймаут рукопожатия):

   ```powershell
   python -c "import socket, ssl; h='foundation-models.api.cloud.ru'; s=socket.create_connection((h, 443), 15); ssl.create_default_context().wrap_socket(s, server_hostname=h).close(); print('TLS ok')"
   ```

5. В `.env`: `LLM_PROVIDER=cloudru` и заполненный `CLOUDRU_API_KEY`.
6. Модель по шагам:

   ```powershell
   python run.py llm
   ```

7. Перезапустите бота (TERMINAL 2) — настройки читаются при старте.
8. Пройдите тот же smoke-test (§14) и сравните с OpenRouter:
   - консультант получает ход на описании задачи;
   - переход консультант → продавец;
   - подбор: карточки только из подбора ядра, без «сейчас подберу» вместо товара;
   - полный путь до предзаказа.

   Стенограммы для сравнения:

   ```powershell
   python run.py dialogs --last 60 --export data\run-cloudru.md
   ```

Сбой на OpenRouter не списывайте на архитектуру, а сбой на Cloud.ru — на модель, пока
тот же сценарий не пройден на обоих провайдерах.

### H. Автотест сценариев через Telegram

Третий терминал; бот уже запущен в TERMINAL 2. Тестировщик — модель OpenRouter
`deepseek/deepseek-chat-v3-0324` — играет клиента из сценария и пишет боту с **отдельного
тестового аккаунта** Telegram. Перед каждым сценарием он жмёт «Начать заново», поэтому
корзина и история этого аккаунта стираются.

Один раз:

1. Тестовым аккаунтом откройте https://my.telegram.org → API development tools, создайте
   приложение (название любое) и впишите в `.env`: `TELEGRAM_API_ID=` и `TELEGRAM_API_HASH=`.
2. Пакет Telethon:

   ```powershell
   .venv\Scripts\python.exe -m pip install telethon
   ```

3. Вход — телефон и код из Telegram вводите сами. Вводите **номер телефона тестового
   аккаунта**, не токен бота: бот не может писать боту (`USER_BOT_TO_BOT_DISABLED`), и вход
   ботом прогон теперь не принимает. Сессия сохраняется в `data\qa\tester.session`: это ключ
   от аккаунта, никому не передавать.

   ```powershell
   .venv\Scripts\python.exe run.py scenarios --login
   ```

Прогон. По умолчанию берутся все 100 сценариев из `tests\scenarios\vdm_100_scenarios.md` —
полный файл заказчика, сверенный с частями 1–25 и 76–100:

```powershell
.venv\Scripts\python.exe run.py scenarios --only 1-5
```

| Параметр | Что делает |
|---|---|
| `файл [файл]` | markdown со сценариями; полный и урезанный файл одних сценариев — вместе, они сводятся |
| `--only 1-10,15` | номера сценариев; без него — все |
| `--mode main+1` | основной путь и одна ветка по очереди (по умолчанию); `main` — только основной; `all` — все ветки |
| `--turns 8` | лимит реплик тестировщика в одном диалоге |
| `--until 06:40` | не начинать новый диалог после этого времени |
| `--out data\qa\run-…` | папка прогона; та же папка — продолжить после остановки |
| `--quiet 8`, `--timeout 300` | секунды тишины после ответа бота и предел ожидания хода |
| `--model …` | другая модель OpenRouter (или `QA_MODEL` в `.env`) |
| `--judge-model …` | модель судьи (или `QA_JUDGE_MODEL`); по умолчанию та же, что у тестировщика |

**Тестовый режим бота.** Чтобы предзаказы тестового аккаунта не уходили менеджеру, впишите его Telegram id в
`.env` **бота** — `QA_USER_IDS=123456789` — и перезапустите бота. Id показывает любой бот вида «userinfo».
Ночью 14.09 без этого тестировщик оформил четыре предзаказа, один — с выдуманным телефоном. Перед каждым
сценарием тестировщик сбрасывает разговор командой `/restart` и подтверждением.

Результат — `data\qa\run-ДАТА-ВРЕМЯ\report.md`, пересобирается после каждого диалога, и
`results.jsonl` рядом. В отчёте: итог (средняя оценка, цель достигнута, время ответа),
сводная таблица, частые проблемы и стенограммы с замечаниями по ходам.

Код проверяет каждый ответ: нет ответа; ответ дольше 60 и 180 с; текст ошибки; markdown;
цена и код 1С карточки и строки списка — против каталога; пункты перечня — против приказов;
пришёл ли файл после «Скачать…»; дубли и повторы. С 15.09 ещё: файл не по разделу из ответа,
раздел для другого возраста, слова не на русском, карточка не из списка ответа, кнопка менеджера
без менеджера, предзаказ на 0 ₽, «передал» без заявки. Судья ставит 1–5 и отмечает, достигнута ли
цель, удержан ли контекст, отработана ли ветка и где бот сбился. **«Цель достигнута» в итоге — только
если так сказал судья и в диалоге нет ошибок проверок**: ночью 14.09 судья засчитал 79 из 100, в том
числе диалоги с неверным файлом. Мнение судьи — отдельным столбцом.

Время. Ночь 14–15.09 (Cloud.ru, `--mode main --turns 6`): 100 диалогов за 3,7 часа, медиана диалога
2 минуты, ход модели — медиана 20 с, максимум 100 с; расход бота ≈ 118 ₽. Основной путь и ветка
(200 диалогов) — около 8 часов. Сначала идут основные пути всех сценариев, потом ветки.
`Ctrl+C` или `--until` останавливают прогон, отчёт остаётся, тот же `--out` продолжает; диалоги,
сорвавшиеся до первого ответа, при продолжении проходят заново.

На ночь — VPN РФ, бот запущен в TERMINAL 2, сон компьютера выключен:

```powershell
.venv\Scripts\python.exe run.py scenarios --mode main --turns 6 --until 06:40 --out data\qa\night-1
```

Первые пять минут посмотрите на экран: под VPN РФ должны отвечать и Telegram, и OpenRouter (на
нём тестировщик и судья). Если бот три диалога подряд не отвечает, прогон останавливается сам.
Следующей ночью — та же команда с `--mode main+1`: готовые основные пути пропускаются, идут ветки.

**50 сценариев по ходам (15.09).** Файлы `tests\scenarios\vdm_50_scenarios_full.md` (все ответы бота) и
`vdm_50_scenarios_autotest_trimmed.md` (часть ответов заменена на «[БОТ ДОЛЖЕН СГЕНЕРИРОВАТЬ: …]»). Реплики
клиента в них одинаковые, поэтому оба файла даются **одной командой** и сводятся в один прогон: 50 диалогов, а не
100 одинаковых. Реплики клиента уходят как написаны, по 11 на диалог, без тестировщика-модели; `--mode` и
`--turns` к ним не применяются. Судья получает по каждому ходу ожидание из урезанного файла, эталонный ответ из
полного и список «Что проверяет сценарий».

Перед ночью: каталог — прайс 1С от 15.09 (версия `2026-09-15-003`; вернуть прежний —
`run.py catalog rollback 2026-09-15-002`), бот перезапущен, в `.env` бота вписан `QA_USER_IDS` — id печатает
`run.py scenarios --login`. Проба на двух сценариях, затем ночь (около 4 часов: 11 ходов по ~25 с):

```powershell
.venv\Scripts\python.exe run.py scenarios tests\scenarios\vdm_50_scenarios_autotest_trimmed.md tests\scenarios\vdm_50_scenarios_full.md --only 1,31 --out data\qa\probe-50
.venv\Scripts\python.exe run.py scenarios tests\scenarios\vdm_50_scenarios_autotest_trimmed.md tests\scenarios\vdm_50_scenarios_full.md --until 06:40 --out data\qa\night-2
```

Как читать отчёт этих сценариев:
- ходы 4–11 одинаковы во всех 50 сценариях, ход 7 собран из шаблона («У меня бюджет доставка, а если…»), поэтому
  повторы между диалогами ожидаемы; различаются только ходы 1–3;
- реплики не подстраиваются под бота: «Подробнее по первой» придёт, даже если товары не показаны — смотрим, как
  бот выкрутился;
- эталонные ответы — шаблоны с условиями, которых у магазина нет: «скидка 5–10 % от 150 000», «доставка по
  Москве бесплатна от 100 000», «сертификаты на каждую позицию». Бот, повторивший их, ошибается: проверка
  «скидка или бесплатная доставка без источника» ловит это кодом, судья предупреждён;
- приветствие (ход 1 в файлах) не сверяется: перед диалогом бот сбрасывается `/restart`;
- бот замолчал два хода подряд — диалог закрывается, остаток не ждём по 5 минут на реплику.

### Фотографии товаров

В выгрузке 1С изображений нет — парсер добирает с сайта адреса снимков, сами файлы
и характеристики (код 1С, страна, сертификат ЕАС). Цены и номенклатуру он не трогает.

Telegram забрать картинку с vdm.ru не может (`failed to get HTTP URL content`),
поэтому для Telegram нужны **файлы** в `data\media\<код 1С>\`.

С машины вне РФ vdm.ru не открывается. Сначала проверьте, что сайт виден именно из
окружения проекта:

```powershell
python -c "import urllib.request; print(urllib.request.urlopen('https://vdm.ru/', timeout=10).status)"
```

Ожидаемо `200`. Затем:

```powershell
python run.py media --cards 20
```

```powershell
python run.py media
```

Пробный прогон — полминуты, весь каталог — около полутора часов. `Ctrl+C`
сохраняет собранное, повторный запуск продолжает с места остановки. После трёх
подряд неудачных страниц обход останавливается сам.

| Команда | Что делает |
|---|---|
| `python run.py media --in-stock` | Только товары в наличии, около получаса |
| `python run.py media --sync` | Перелить собранное в базу знаний без обращения к сайту |
| `python run.py media --dedupe` | Убрать одинаковые снимки внутри папки товара |
| `python run.py media --listing <адрес раздела> --cards 0` | Быстрый прогрев превью по странице раздела |

Где лежит собранное:

| Где | Что |
|---|---|
| `data/vdm.sqlite3`, `product_media`, `product_attributes` | Кэш обхода и характеристики |
| `data/media/<код 1С>/1.jpg` | Файлы снимков — из них шлёт фото Telegram |

Перезапустите бота после прохода: движок собирается при старте.

## 19. Журнал диалогов

Пишется по файлу на сутки в `data\dialogs\`. Персональные данные обезличиваются
до записи, ответы на шагах контактов не пишутся. Отключается
`DIALOG_LOG_ENABLED=0`.

```powershell
python run.py dialogs --last 20
```

```powershell
python run.py dialogs --channel telegram
```

```powershell
python run.py dialogs --last 50 --export data\dialogs.md
```

В каждом ходе с моделью:

- `usage` — провайдер, модель, токены, обращения за ход, рубли. Цены — `*_PRICE_IN`
  и `*_PRICE_OUT` в `.env`; у OpenRouter в шаблоне стоят нули, расход не считается;
- `route`:
  - `role` — `consult`, `sell` или `guard`;
  - `intent` — намерение реплики (`FULL_EQUIPMENT_SET`, `PRODUCT_SEARCH`, `PRICE_REQUEST`…);
  - `previous_agent` — кто отвечал прошлым ходом; `reason` — почему выбран агент;
  - `stage`, `objection` — этап и возражение;
  - `routed_by` — `правило`, `модель` или `запасной` (модель маршрутизации недоступна —
    отвечает прежний агент, в начале разговора консультант);
  - `cards.reason` — почему карточки показаны или нет;
  - `norm_lookups` — какие пункты и в каком приказе искали;
  - `false_promise` и `fallback` — продавец пообещал подбор без подбора, и чем ответ
    заменён: `procurement_select` (подбор ядра) или `question` (уточняющий вопрос);
  - `discarded_answer` — ответ дважды не прошёл проверку цен и оснований.
